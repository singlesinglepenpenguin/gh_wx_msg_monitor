# 微信群接龙工具：故障记录与排查指南

本文件记录 2026-10-27 本机实际遇到的问题。发生新问题时，先确认出错阶段，再按对应错误处理；不要把“初始化失败”“群名未匹配”“消息为零”混为一谈。

## 微信可以一直开着吗？

可以。日常使用时让微信保持登录、接收新消息即可，不需要反复退出登录。

“开始抓取”是**一次性初始化密钥**时的计时按钮：沿用 gh_ui 的新版初始化，在短时间内捕获数据库读取密钥，完成后调试器退出。此次已保存有效密钥，日常读取直接使用保存的凭据解密本地数据库。微信可以一直开着，也不需要停留在目标群。

只有换账号、升级后凭据失效、或必需库缺少密钥时，才排查是否需要补充初始化。不要把调试器做成长时间常驻监听，也不要对每次读取自动重复抓取。

工具的自动更新是另一个功能：目前勾选“窗口保持打开时自动更新”后，在北京时间 09:00、15:00 的前五分钟内各执行一次。电脑和工具窗口要保持运行；每次重新打开需重新勾选。它目前没有安装开机启动或关闭窗口后运行的后台服务。电脑休眠、微信退出或断网时，不能据此承诺持续收到新消息；之后手动更新会从上次成功进度补读本地已有消息。

## 先确定卡在哪一步

| 阶段 | 成功证据 | 失败时先查什么 |
|---|---|---|
| 账号与目录 | 当前登录微信号与实际打开的 wxid 目录对应 | 微信号不一定等于目录名，多账号不能猜选 |
| 系统授权/启动脚本 | 辅助脚本正常启动 | 原始错误是找不到文件，还是 Operation not permitted |
| 进程读取权限 | task_for_pid 成功、get-task-allow 已生效 | 原版修复是否完成，微信是否重新启动 |
| 一次性密钥抓取 | 断点实际命中，密钥通过数据库 HMAC 校验 | 断点解析成功不等于发生调用；候选密钥也不等于有效密钥 |
| 解密与刷新 | 所需消息、通讯录、会话库解密，WAL 合并与完整性检查成功 | 具体缺哪个库的密钥、哪个库失败 |
| 群定位 | 完整群名精确匹配一个会话 | 正确账号、contact.db 是否可读、群名是否一致 |
| 接龙查询 | 目标群与时间范围内返回真实消息 | 时间区间、#接龙、正文是否完整 |
| Excel 更新 | 原文件更新并保存归档、进度 | 文件占用、表头、匹配歧义、并发更新 |

## 本次实际卡点与处理

### HELPER_PATH：文件存在，却报找不到 _mac_helper.py

**当时错误**：`can't open file '\"/.../_mac_helper.py\"': [Errno 2] No such file or directory`。

**定位结果**：辅助脚本实际存在。shell 参数的引号被重复转义，Python 收到的文件名包含字面双引号，不是缺文件。

**处理**：仅修复普通初始化命令的参数引用，使用 shlex.join；解释器、授权、辅助脚本及扫描参数保持原流程。最新版已修复。再次遇到时先查真实文件及错误中的完整路径，不要盲目补文件或复制脚本到其他位置。

### EXECUTION_CONTEXT：ps 被拒绝、AppleScript -2740

**当时错误**：`PermissionError: [Errno 1] Operation not permitted: '/bin/ps'`；此前也遇到过 AppleScript `-2740`。

**定位结果**：早期执行环境不能进行进程检查/系统授权，尚未进入微信扫描。这与微信群有没有数据无关。后来 Full access 生效，原进程检查才可执行。

**处理**：从 Finder 双击本地应用运行，再核对真实错误。Codex Full access、终端权限和 macOS 隐私授权是不同层次。不能用“我已经勾选 Full access”替代实际执行结果，也不要据此认定微信还在运行。

### SYSTEM_FILE_ACCESS / APP_PERMISSION：系统拒绝读取脚本或修改微信

**当时错误**：`Operation not permitted`、`APP_PERMISSION_DENIED`；内核日志分别记录辅助脚本的 `file-read-data` 拒绝，以及微信 CodeResources 的 `file-write-data` 拒绝。

**定位结果**：Terminal 的完全磁盘访问和 App 管理已经允许，但提权后的责任进程被系统归到苹果的 `authtrampoline`。最初用户开启的 Python 是另一个工具的虚拟环境，并非本次调用的系统 Python。因此反复给 Terminal 或错误的 Python 授权没有解决问题。

**排查/处理顺序**：

1. 分清是读脚本被拒绝，还是重签名写微信应用被拒绝；先保留完整错误。
2. 在“系统设置 → 隐私与安全性”核对“完全磁盘访问权限”；修复应用签名被拒绝时还需核对“App 管理”。
3. 若已开启仍失败，查看系统日志中的 `responsible` / `accessing`，确认实际权限归属，再授权对应程序。不要把不同的 Python 当成同一个程序。
4. **本机这次**确认归属为下面的系统程序后，在“完全磁盘访问权限”点 `+`、按 `⌘⇧G` 输入此路径，添加并开启，随后重试成功：

   ```text
   /System/Library/Frameworks/Security.framework/authtrampoline
   ```

5. 这个路径是本次实测结论，不保证其他电脑必然相同；以其实际日志为准。

本次没有 App Store receipt，原始签名检查通过。仅凭 APP_PERMISSION_DENIED 不能认定是 App Store 版，更不能要求用户先卸载微信。

### WECHAT_PROCESS_ACCESS：task_for_pid kr=5

**当时错误**：`task_for_pid(...) kr=5 errno=0`，密钥数为 0。

**定位结果**：辅助脚本已能启动，但微信签名中 get-task-allow 为 false，进程内存读取仍被拒绝。

**处理**：先正常退出整个微信应用，再调用 gh_ui 原有“修复 Mac 读取权限”，成功后重新打开并登录，再初始化。本次原版修复返回 OK 后 get-task-allow=true，进程读取成功。

正常退出请求曾返回 `User canceled (-128)`，但复查发现进程实际已退出。因此应复查进程状态，不要只凭提示强制结束微信。若修复返回 WECHAT_RUNNING，先正常退出再试。

### KEY_CAPTURE：连接成功、断点已就位，但 0 命中

**当时现象**：lldb 成功连接当前微信，两个函数都解析到断点位置，但 `aes_hits=0`、`kdf_hits=0`。

**能够确认的原因**：这两个函数在抓取窗口内没有触发；因此没有有效密钥，无法执行后续解密。不能从 0 命中推断群没有数据，也不能直接归咎于用户没操作。

**本次排除与处理**：

- 原版脚本在独立测试程序 3 秒命中 28 次，证明本机回调机制可用；这是测试程序，不能冒充真实微信读取。
- 补充原生断点次数、Continue 状态与架构日志，保持原有断点和抓取方式，确认微信正常运行。
- 当前聊天可能已在内存中，打开/滚动界面不一定新读加密数据库；这是可能原因，不能仅凭 0 命中定论。
- 有一次真实读库窗口命中 47 次，取得 4 个有效库密钥，说明采集方式和当前账号可以工作。
- 需要补开库密钥时，先停在登录界面，再同步启动抓取并登录；聊天提示与用户操作时机曾错开，多次窗口结束时微信仍在登录界面、账号数据库尚未打开。
- 后改用本机“开始抓取”按钮同步计时，登录附近命中 AES 145 次、KDF 18 次。本次没有取得通用口令，但候选经校验后累计覆盖 13 个库，已足够完成本工具读取。

**处理办法**：先使用保存的凭据测试连接；确实缺密钥时，普通扫描后再按原版说明使用一次性新版初始化。需要登录配合时，用本机提示同步计时，不反复盲抓。新版初始化会附加调试器，有原版说明的安全验证风险，工具应要求用户主动确认；日常查询不附加调试器。

### ACCOUNT_PATH：jimmyxhb 的目录不叫 jimmyxhb

**本机实测**：运行的是 `/Applications/WeChat.app` 主进程；lsof 确认它打开 `wxid_304xm7nmzhw522_b2a4/db_storage` 中的库。用户先核对当前资料，之后通过解密后 contact.alias 直接确认 `jimmyxhb → wxid_304xm7nmzhw522`。

本机账号目录：

```text
~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/wxid_304xm7nmzhw522_b2a4/db_storage
```

**处理**：多账号时先核对当前资料，再对照当前微信进程实际打开的目录；拿到通讯录后再核对 alias。不能仅凭“第一个目录”或“数据量大”猜选。全进程抓取断点阶段不使用账号目录，因此选错目录不能解释断点原生计数为 0；但会导致后续密钥校验/群定位失败。

### KEY_COVERAGE / GROUP_MATCH：能解密消息，但群名匹配为 0

**当时现象**：取得 4 个有效密钥，消息库与会话库解密成功，列出 45 个会话；群名匹配为 0。

**定位结果**：缺 contact.db 密钥，上游群名索引无法从会话 hash 还原显示名。后续查询确实返回了真实接龙，但当时尚不能把它们归属为目标群。

**处理**：保留已有密钥，在同一账号下增量补抓必需库。不要删除已有凭据，不要凭消息内容猜群。通讯录解密后再精确定位。本次补齐后准确匹配唯一的“GH派点反馈群”。

### SQLITE_INDEX：SQL logic error

**当时现象**：上游已能解密和定位群，但工具自己的 refresh 在 `PRAGMA quick_check` 抛出 `sqlite3.OperationalError: SQL logic error`。

**定位结果**：业务层把 contact_fts.db 也列为必需库。该专用全文检索索引在系统 SQLite 检查时失败；contact.db、session.db、message_0.db 的同一检查全部为 ok。

**处理**：业务层仅把实际读取的核心库列为必需并检查完整性，不用未消费的 FTS 索引阻断消息读取。没有跳过消息、通讯录和会话核心库的密钥或完整性校验。最新版已修复。再次出现其他 SQL logic error 时，应记录具体库与调用位置，不能一律当作同一原因。

## 记录在哪里，反馈什么

- **排错指南**按钮打开本文件；应用打包时一并包含。
- **故障记录**按钮打开 local_data。后续运行失败会追加到 `local_data/error_message.jsonl`，每行包含北京时间、操作、错误编号、建议、异常类型、原始错误与调用位置。
- 故障记录只写本机，文件仅当前用户读写；长十六进制候选密钥在写入前过滤。记录仍可能有本地路径和业务错误，请按需反馈，不要公开发布 local_data。
- 日志保存失败时，报错窗口仍保留原始异常，并告知记录未能落盘。无故障时不制造模拟运行故障记录。
- 反馈时提供错误编号、出错时间、正在做的操作、微信版本及对应故障条目；不要发送 wechat.json、all_keys.json 或完整微信数据库。
- 本次逐步实测结果见 `docs/验证结果.md`；`docs/diagnostics` 中保留本机诊断证据，不是日常用户必须操作的文件。
